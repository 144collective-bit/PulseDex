# Migrations

Every file in `supabase/migrations/` is run by hand, in the Supabase SQL
editor, in numeric order. There is no migration runner in this project and
that is a deliberate consequence of where it is deployed: the app is a static
bundle plus serverless functions, neither of which has a place to run one from
or a lock to run it under.

All of them are safe to run twice. That is not a convention, it is a
requirement — with no runner there is no record of what has been applied, so
the only way to be sure is to be able to run everything again.

## The outstanding ones

**`0017_message_reply_fk.sql` must run before the current branch merges.**
Without it every room reports that it could not be loaded. `0012` created the
`reply_to` column and its foreign key in one statement:

```sql
alter table public.messages
  add column if not exists reply_to bigint references public.messages(id)
  on delete set null;
```

`add column if not exists` is one statement and the `references` clause is
part of it, so on a database where the column already exists the whole thing
is skipped — the constraint included, and silently. The chat reads every
message with an embed that names that constraint, so the schema cache has
nothing to resolve it against.

The lesson worth keeping past this file: **a constraint an application names
by string should be created by that name, in its own statement**, not left to
Postgres's default naming as a side effect of a column definition.

**`0018_room_admin.sql` is required, not optional.** It adds
`archived_at`/`archived_by` to `rooms`, narrows the anon read policy to live
rooms, and creates `room_gate_changes`.

`ROOM_FIELDS` in `src/config/queries.js` selects `archived_at`, because the
browser filters archived rooms out as well as the policy - two cheap checks
beat one that is right only after somebody has run a migration by hand. A
select naming a column that does not exist fails outright, and every room read
goes through that string, so **without this migration the room list and the
token page's chat tab will not load.**

That is the same failure shape as the missing reply key above, deliberately
so: it fails loudly, at a named place, rather than working in a way that
quietly lists rooms nobody can post in. `/api/health` names the column.

**`0019_profile_depth.sql` is required for the same reason.** It adds
`pinned_post_id`, `first_seen_at`, `first_seen_checked_at` and `show_holdings`
to `profiles`, and `PUBLIC_PROFILE_FIELDS` selects three of them - so without
it every profile page fails on the select rather than quietly going without a
pin. Same trade, taken the same way: two cheap checks that agree beat one that
is right only after somebody has run a migration by hand.

Two things in it are worth knowing before running it.

It **raises** if `follows` does not carry the foreign key names the app selects
by - `follows_follower_fkey` and `follows_followee_fkey`. Those names were
generated by 0008's inline `references` and never written down anywhere, and
Batch 2 reads the follow graph with the person attached, which means naming
them by string. This project has already been taken down once by relying on a
constraint name it never stated, so the check is in the migration, where a
human is watching, rather than left to a page that will not load. If it
raises: rename the existing constraints to those names. Do not add new ones -
two foreign keys on the same column would make the embed ambiguous again,
which is the error this is trying to avoid.

And it adds `pinned_post_id` and its foreign key in **two statements**, which
is the whole lesson of 0017 applied before the fact rather than after. `add
column if not exists ... references ...` is one statement, so on a database
where the column already exists it is skipped entirely - constraint included,
silently. The column goes in with `add column if not exists`; the constraint
goes in separately, guarded on its own name, and the name is given rather than
inherited.

**`0020_posts_worth_making.sql` is required, like the two above it.** It adds
`image_url`, `image_w`, `image_h`, `edited_at` and `quote_id` to `posts`, and
creates `post_reactions`, `post_bookmarks` and `link_previews`. `POST_FIELDS`
selects every one of those columns and embeds `post_reactions`, and every read
of a post in the app goes through that string - so without this migration the
feed, every profile and every post page fail on the select.

Three things in it are worth knowing before running it.

It adds `quote_id` and its foreign key in **two statements**, which is the
third time this file has had to say so. `add column if not exists ...
references ...` is one statement and is skipped whole when the column already
exists, taking the constraint with it, silently. That is what `0012` did to
`messages.reply_to` and what `0017` exists to repair.

**`post_bookmarks` has no row-level security policy at all** - not for `anon`,
not for `authenticated`, read or write. That blank space is the entire security
model for the table and is deliberate: with RLS enabled, an operation no policy
permits is refused, so the anon key that ships in the bundle can do nothing
there. Every read goes through `api/_routes/posts/bookmarks.js` with the
service role and an address taken from the sign-in cookie.

The reason it has to work that way is the one `0010` wrote down for
`notifications`, and it is the thing most likely to be got wrong by whoever
adds the next private feature: sign-in here is a wallet signature and a JWT
this app sets in a cookie, **not Supabase auth**. So `auth.uid()` is null in
every request the browser makes, and a policy saying
`using (address = auth.uid())` would not restrict `post_bookmarks` - it would
empty it. If somebody later adds `using (true)` to make a query work from the
browser, they will have published every bookmark on the site.

**`link_previews` deliberately has no image column.** An og:image is the
obvious thing to put in a preview and the one thing that would undo the reason
previews are fetched server-side: rendering it means the reader's browser
requests it from the linked site, handing that site the IP address of everybody
who scrolled past the post. If an image is ever wanted there, re-host it; do
not add a column that holds somebody else's URL and hand it to an `<img>`.

**`0021_safety_at_scale.sql` is required, like the three above it.** It adds
`hidden_at` and `hidden_by` to `posts`, and creates `muted` and
`moderation_log`. `POST_FIELDS` selects both new columns, and every read of a
post goes through that string - so without this migration the feed, every
profile and every post page fail on the select, exactly as they would without
0020.

Four things in it are worth knowing before running it.

**A hide is a visibility measure and never a containment one.** This is the
thing most likely to be misread from the column name, so the migration says it
and so does every file that touches it. The anon read policy on `posts` is
`using (deleted_at is null)` and is deliberately **not** narrowed to
`hidden_at is null`. It cannot be: row-level security has no identity to
compare against here, so a policy that hid these rows would hide them from
their own author too - and an author who is not told their post is pending
review has simply had it disappear. So a hidden post still comes back from the
database, and what implements the hide is the query filter in
`src/services/posts.js` plus what the interface draws. Anybody determined
enough to read the database with the anon key can still see it. If a post needs
to be genuinely unreadable, that is `deleted_at`, which the policy does
enforce.

**`muted` and `moderation_log` have no row-level security policy at all** -
not for `anon`, not for `authenticated`, read or write. The same blank space as
`post_bookmarks` and `blocked`, for two different reasons worth separating.
`muted` is private because "who I cannot stand" is a list about the reader
rather than about the people on it, and a site where accounts are wallet
addresses publishing it would publish a graph of who refuses to read whom.
`moderation_log` is private because it is a list of actions taken against named
addresses with a moderator's note attached, which a select policy would publish
to everybody including the people in it.

**`moderation_log` has no foreign keys**, which is not an oversight. A
`references posts(id) on delete cascade` would mean a hard delete of a post
erased the record that somebody removed it - precisely the record worth
keeping. The log has to outlive what it describes. For the same reason `actor`
does not reference `profiles`: a moderator is an address in an environment
variable and may never have posted, and a log entry that could not be written
because the actor had no profile row is a log with holes exactly where somebody
was moderating without posting.

It is also **append-only by discipline rather than by constraint**. The service
role can update and delete anything, so nothing in the schema makes the table
immutable. What keeps it append-only is that exactly one module writes it -
`logAction` in `api/_lib/moderation.js` - and that module only inserts.

Finally, it **asserts a foreign key name it did not create**:
`post_reports_reporter_fkey`, declared inline by 0005 and therefore named by
Postgres rather than by us. Auto-hide reads a post's reporters with each
reporter's `first_seen_at` attached, which needs that name in the select. The
migration raises if it is absent, so the assumption fails while somebody is
running a migration rather than later, on the first report after a deploy. The
two foreign keys 0021 creates itself are named explicitly, which is the lesson
from having had to do this twice.

## Checking one ran

Each file ends with a query that says whether it worked, without deploying
anything. `api/_routes/health.js` is the other half: it runs every select
string in `src/config/queries.js` against the real database and names the one
that failed, which is what turns "the rooms will not load" into "this
constraint is missing".
